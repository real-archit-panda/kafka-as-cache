Landscape

Popular ways to cache

In-App (In-Memory) Cache

A map living inside the application process (e.g. Caffeine, Guava, a HashMap). Fastest possible reads — no network. But it dies with the process and each instance has its own copy (no sharing).

Fast · Local · Not shared · Volatile

Distributed Cache (Redis / Memcached)

A dedicated cache server (or cluster) that all app instances share over the network. Consistent view, survives app restarts, scales independently — but it's extra infrastructure to run, secure and pay for.

Shared · Network hop · Extra infra

CDN / Edge Cache

Caches responses close to users at edge locations (CloudFront, Cloudflare). Great for static assets and read-heavy HTTP responses; keyed by URL, not arbitrary application state.

Geo-distributed · HTTP · Read-heavy

Database / Query-Result Cache

Caching at or in front of the database — materialized views, query caches, or a read-through cache layer. Reduces load on the primary store; invalidation is the hard part.

Read-through · Reduces DB load · Invalidation is tricky
The Case Against Reaching for Redis

Redis is great — but not free, and not always the right fit

🏗️

Operational overhead

  • Another system to deploy, monitor, patch and upgrade
  • HA needs replicas + Sentinel / Cluster — real ops burden
  • One more thing that can page you at 3am
💸

Cost & footprint

  • Redis is RAM-resident, and memory is the most expensive storage tier
  • Managed Redis is billed per node, per hour — the meter never stops
  • Growing the dataset means scaling the most expensive resource (RAM)
  • RAM is blazing fast — but not every workload needs sub-millisecond reads; you often pay for speed you don't use
🔗

Consistency & coupling

  • Cache invalidation — the classic hard problem; stale data & dual-write bugs
  • Two sources of truth (DB + cache) to keep in sync
  • Durability is opt-in (RDB/AOF); a crash can lose recent writes
  • Network hop + an extra failure mode between app and cache

If you already run Kafka, the cache rides on infrastructure you already operate, secure and pay for — no new moving part, and the data is durable & replicated by default.

Redis still wins for sub-millisecond random reads, rich data structures (sorted sets, TTLs, pub/sub) and pure ephemeral caching. The point isn't “never Redis” — it's “not automatically Redis.”

The Idea

Why Use Kafka as a Distributed Store?

1 No new infrastructure

Already using Kafka for event streaming? Then adding a cache means zero new systems to stand up. The store is just a library running inside your app — nothing extra to deploy, secure or pay for.

2 Survives node failures

Kafka replicates every write across brokers automatically. If a broker — or your whole app — crashes, nothing is lost: the cache is simply rebuilt from the log. Durability comes for free.

3 Scales horizontally

Need more capacity or throughput? Add more partitions and more app instances. Kafka Streams splits the keyspace across them automatically — each instance owns and serves its own slice.

4 History + latest value

A compacted topic keeps the latest value per key, while the log still records every change as it happened. You get a clean current-state view and the change history behind it.

Works especially well for ⚙️ Configuration & feature flags 🔑 Session storage ⚡ Caching frequently-accessed data 🌐 Distributed application state
What's a compacted topic? A normal topic deletes old messages after a time window. A compacted topic instead keeps only the latest message per key, forever — so the log of changes collapses into a current-state table.
How It Works

The architecture: two paths, one source of truth

✏️ Write path

put(key, value) produces a record to the compacted topic. The app never writes RocksDB directly — the write goes to Kafka first, so it's durable and replicated before it's acknowledged.

⚡ Read path

get(key) reads the local RocksDB that Kafka Streams keeps in sync — an in-process lookup with no network hop. This is the fast, cache-like part.

⏳ The one gotcha

A write travels producer → topic → Streams → RocksDB, so it isn't instantly readable. That millisecond gap is the eventual-consistency window.

Notes: Kafka Streams is a library running inside your app (not a server) — it consumes the compacted topic and applies each record as an upsert (key,null = delete), and auto-shares partitions across instances via the application-id. RocksDB is an embedded KV store shipped with Kafka Streams (not part of the broker), living on each instance's own disk; it's a disposable local copy — the topic is the source of truth, so wiping RocksDB and restarting rebuilds it by replaying the topic.

Resilience

What happens when things crash?

Because the compacted topic is the source of truth and RocksDB is only a disposable local copy, every failure recovers with no data loss. The next slides walk through each scenario.

💥 crash  →  🗑️ local copy gone  →  🟠 topic intact  →  ♻️ rebuilt from the log
💥 App / pod crashes 🗑️ RocksDB wiped 🔀 One of many pods dies 🖥️ A Kafka broker dies ⚡ Crash mid-write
Crash Scenario 1 / 5

💥 App / pod crashes

What's lost: the pod's in-memory state and — if its disk is ephemeral — its RocksDB files.

Recovery: restart the pod. Kafka Streams re-joins, replays the topic from the last checkpoint, and rebuilds RocksDB. Data returns intact.

✓ verified in our test suite: hard kill -9 + restart → all keys recovered
Crash Scenario 2 / 5

🗑️ RocksDB wiped / lost

What's lost: only the local indexed copy — e.g. the disk was cleared or the node reprovisioned.

Recovery: on next start the store is rebuilt entirely from the topic. The truth was never in RocksDB — it's just a cache.

✓ verified: deleted the whole state dir + restart → data fully rebuilt
Crash Scenario 3 / 5

🔀 One of many pods dies

What's lost: the partitions that pod owned become temporarily unserved.

Recovery: a consumer-group rebalance reassigns those partitions to surviving pods, which rebuild that slice from the log.

optional standby replicas keep warm copies → near-instant failover
Crash Scenario 4 / 5

🖥️ A Kafka broker dies

What's lost: nothing served by that broker — provided replication factor > 1.

Recovery: a replica on another broker is automatically promoted to leader. The topic — the source of truth — stays available.

requires replication factor ≥ 2 (our local demo ran a single broker, RF 1)
Crash Scenario 5 / 5

⚡ Crash mid-write

What's lost: an unacknowledged write may or may not have landed on the broker.

Recovery: with acks=all a write is only “done” once replicated. A failed send() is retried or surfaced as an error — never a silent partial state.

synchronous send().get() + broker acknowledgement
The Obvious Objection

“If it's on disk, how is it fast?”

Disk-based doesn't mean disk-speed. Both Kafka and RocksDB are engineered so that the hot path barely touches the disk — and reads never touch the network.

➡️ Sequential, not random

Kafka only ever appends to the end of a log file. Sequential disk I/O is orders of magnitude faster than random seeks — no in-place updates, no B-tree churn.

🧠 OS page cache = free RAM

Recently-written/read data stays in the OS page cache (RAM). Hot reads are served from memory without Kafka managing any cache itself — the OS does it.

💾 RocksDB keeps hot data in memory

Our reads hit RocksDB, which has an in-memory block cache + memtable. Hot keys are answered at memory speed; only cold keys touch local SSD.

🔌 No network hop on reads

get(key) is an in-process lookup in local RocksDB. Redis always pays a network round-trip; here the data is already on the box.

📤 Zero-copy transfer

Kafka streams bytes straight from the page cache to the socket via sendfile() — skipping copies through the application. Very little CPU per byte.

⚖️ The honest bit

A cold key not in any cache does hit disk — slower than Redis's always-RAM guarantee, but it's local SSD, not the network. And it still crushes a database query.

Rule of thumb: hot data ≈ memory speed (page cache + RocksDB cache) · cold data = one local disk read · reads never cross the network.

Reach for Redis when… pure ephemeral caching, sub-ms & uniform latency, high random-read rates, or you need rich data structures.
Reach for Kafka-as-cache when… you already run Kafka, want durability & replication for free, and can tolerate a small eventual-consistency window.

Redis is faster and more consistent for pure caching. Kafka-as-cache trades a little write latency and read-throughput for durability, replication, and zero new infrastructure — with the bonus that reads are local, with no network hop.
